# 커밋

작업 트리의 변경사항을 읽고, 목적이 같은 변경끼리 묶어, 한국어 커밋 메시지로 커밋한다.
커밋은 이력에 남고 되돌리기 번거롭다. 그래서 커밋 계획을 사용자에게 보여 주고 승인을 받은 뒤에만 실행한다.

## 절차

### 1. 변경사항 분석

아래 명령으로 변경 전체를 파악한다. 스테이징 여부와 관계없이 모든 변경을 대상으로 한다.

```bash
git status --porcelain
git diff                 # 스테이징되지 않은 변경
git diff --cached        # 이미 스테이징된 변경
git log --oneline -10    # 기존 메시지 스타일 참고
```

새 파일(untracked)은 diff에 나오지 않으므로 Read로 내용을 직접 읽는다.
변경이 하나도 없으면 "커밋할 변경사항이 없습니다"라고 알리고 끝낸다.

파일 이름과 diff 통계만 보고 판단하지 않는다. 같은 파일 안에서도 기능 추가와 버그 수정이 섞여 있을 수 있어서, 실제 변경된 줄을 읽어야 목적을 알 수 있다.

### 2. 논리적 단위로 분류

한 커밋에는 한 가지 목적만 담는다. 목적이 다른 변경을 한 커밋에 섞으면 리뷰어가 의도를 파악하기 어렵고, 되돌리거나 bisect할 때 다른 변경까지 끌려간다.

묶는 기준:
- 하나의 기능을 위해 함께 바뀐 파일(구현, 타입, 그 기능의 테스트)은 한 단위다.
- 기능과 무관한 버그 수정은 별도 단위다.
- 의존성 추가와 그에 따른 lock 파일 변경은 한 단위다. 그 의존성을 쓰는 기능 코드는 기능 단위에 넣는다.
- 설정, 빌드, 문서, 포맷팅 변경은 동작 변경과 분리한다.

한 파일 안에 성격이 다른 변경이 섞여 있으면 파일 단위로 나눌 수 없다. 이때는 더 큰 목적 쪽 단위에 넣고, 계획에서 "이 파일에는 ~ 변경도 함께 들어 있습니다"라고 알린다. hunk 단위 분리는 사용자가 요청할 때만 `git apply --cached`로 시도한다.

커밋에서 제외할 파일:
- 비밀 정보가 들어 있는 파일(`.env`, 키 파일, 토큰이 적힌 설정). 값이 더미로 보여도 제외하고 알린다. `.gitignore`에 넣을지 사용자에게 묻는다.
- 빌드 산출물, 로그, 에디터 임시 파일.

`git add -A`나 `git add .`는 쓰지 않는다. 의도하지 않은 파일이 섞여 들어가는 가장 흔한 경로다. 커밋마다 파일을 이름으로 지정한다.

### 3. 커밋 메시지 작성

형식:

```
<타입>: <요약>

- <변경 내용과 이유>
- <변경 내용과 이유>
```

타입은 네 가지만 쓴다.

| 타입 | 쓰는 경우 | 예 |
|------|----------|----|
| feat | 사용자가 체감하는 기능 추가, 변경 | `feat: 컴포넌트 미리보기 새로고침 버튼 추가` |
| fix | 잘못된 동작 수정 | `fix: 빈 프롬프트 전송 시 서버 500 오류 수정` |
| refactor | 동작은 같고 구조만 바꿈 | `refactor: API 호출 로직을 useGenerate 훅으로 분리` |
| chore | 그 외 전부(의존성, 설정, 빌드, 문서, 테스트만 변경) | `chore: react-live 의존성 추가` |

요약 규칙:
- 한국어로 쓴다. 코드 식별자, 라이브러리 이름은 원문을 유지한다.
- 50자 안팎으로 쓰고 마침표를 찍지 않는다.
- "무엇을" 했는지 명사형으로 끝낸다("~추가", "~수정", "~분리", "~제거").
- 파일 이름을 나열하지 않는다. 변경의 의미를 쓴다.

본문 규칙:
- 변경 내용과 이유를 불릿으로 쓴다. diff를 보면 알 수 있는 "어떻게"보다, diff만으로는 알 수 없는 "왜"를 우선한다.
- 한 파일의 한두 줄 변경처럼 요약만으로 충분하면 본문을 생략한다.

### 4. 승인 요청

커밋을 실행하기 전에 계획을 아래 형식으로 보여 준다.

```
## 커밋 계획

### 커밋 1/3
feat: 컴포넌트 미리보기 새로고침 버튼 추가

- 애니메이션 컴포넌트를 다시 보려면 리마운트가 필요해 key를 바꾸는 버튼을 추가
- Preview에 refreshKey prop 전달

파일: src/App.tsx, src/components/Preview.tsx

### 커밋 2/3
...

### 제외
- .env: API 키가 들어 있어 커밋하지 않습니다. .gitignore에 추가할까요?

이대로 커밋할까요? 수정할 내용이 있으면 알려 주세요.
```

이미 스테이징된 파일이 있으면 "스테이징 상태는 계획에 맞춰 다시 잡습니다"라고 계획에 적는다. 사용자가 직접 올린 상태를 말없이 바꾸지 않기 위해서다.

사용자가 수정을 요청하면 반영한 계획을 다시 보여 주고 승인을 기다린다. 승인 전에는 `git add`도 하지 않는다.

### 5. 커밋 실행

승인을 받으면 커밋 순서대로 실행한다. 기존 스테이징은 먼저 비운다.

```bash
git restore --staged .
git add <커밋 1 파일들>
git commit -m "<요약>" -m "<본문>"
git add <커밋 2 파일들>
git commit -m "<요약>" -m "<본문>"
```

끝나면 `git log --oneline -<커밋 수>`로 결과를 보여 주고, 제외한 파일이 있으면 다시 알린다.
push는 하지 않는다. 사용자가 따로 요청할 때만 한다.

## 예시

입력(변경 요약):
- `src/components/CodeView.tsx` 새 파일: 생성된 코드를 보여 주는 컴포넌트
- `src/App.tsx`: CodeView 추가, 그리고 `provider` 상태의 초기값 오타(`'anthropc'` → `'anthropic'`) 수정
- `package.json`, `bun.lock`: `prism-react-renderer` 추가

출력(커밋 계획):

```
### 커밋 1/3
chore: prism-react-renderer 의존성 추가

파일: package.json, bun.lock

### 커밋 2/3
feat: 생성된 컴포넌트 코드 보기 패널 추가

- 미리보기 옆에서 코드를 바로 확인할 수 있도록 CodeView 컴포넌트 추가
- prism-react-renderer로 구문 강조

파일: src/components/CodeView.tsx, src/App.tsx

### 커밋 3/3
fix: provider 초기값 오타 수정

- 'anthropc'로 적혀 있어 첫 요청이 실패하던 문제 수정

파일: src/App.tsx
```

App.tsx에 두 목적의 변경이 섞여 있다. 이 경우 커밋 2에 넣고 계획에 "App.tsx에는 provider 오타 수정도 함께 들어 있습니다"라고 알린다. 위처럼 커밋 3으로 나누는 것은 사용자가 hunk 분리를 요청했을 때만 한다.
