# PR 생성

현재 브랜치의 커밋을 읽고 `${CLAUDE_SKILL_DIR}/references/pr-template.md` 형식의 본문을 채워 Draft PR을 만든다.

이 스킬은 분리된 컨텍스트(fork)에서 실행된다. 사용자에게 질문하거나 승인을 받을 수 없다. 그래서 두 가지 원칙을 지킨다.

- 판단이 필요한 지점은 아래 규칙대로 정하고, 무엇을 어떻게 정했는지 최종 보고에 적는다.
- 진행하면 안 되는 상황(아래 "중단 조건")에서는 아무것도 바꾸지 않고 이유만 보고한다.

PR은 Draft로 만든다. 사용자가 본문을 확인한 뒤 직접 Ready for review로 바꾼다. 리뷰 요청은 다른 사람의 시간을 쓰는 일이라 사람이 마지막 확인을 하는 편이 안전하다.

## 절차

### 1. 상태 확인

```bash
git status --porcelain
git branch --show-current
git remote get-url origin
gh auth status
gh repo view --json defaultBranchRef -q .defaultBranchRef.name
gh pr view --json url,state,isDraft 2>/dev/null
```

기준 브랜치는 `$ARGUMENTS`의 첫 단어가 브랜치 이름이면 그것을 쓴다. 아니면 저장소 기본 브랜치를 쓴다. `$ARGUMENTS`의 나머지는 본문에 반영할 추가 요청으로 본다.

### 중단 조건

다음 중 하나라도 해당하면 push와 PR 생성을 하지 않는다. 어떤 조건에 걸렸는지와 사용자가 할 일을 보고하고 끝낸다.

| 조건 | 보고할 내용 |
|------|------------|
| 커밋되지 않은 변경이 있다 | 변경 파일 목록. commit 스킬로 먼저 커밋해 달라고 안내 |
| 현재 브랜치가 기준 브랜치와 같다 | 작업 브랜치를 만들어야 PR을 만들 수 있다고 안내 |
| 기준 브랜치 대비 새 커밋이 없다 | PR에 담을 변경이 없다고 안내 |
| 이미 열린 PR이 있다 | 그 PR의 URL. 새로 만들지 않는다 |
| origin 원격이 없거나 gh 인증이 안 되어 있다 | 설정 방법 안내 |

PR이 커밋되지 않은 변경을 담지 못하는데도 진행하면, 사용자는 PR 본문과 실제 diff가 다른 상태를 보게 된다. 그래서 커밋 여부를 가장 먼저 확인한다.

### 2. 변경 분석

```bash
git fetch origin <기준 브랜치>
git log origin/<기준 브랜치>..HEAD --format='%h %s%n%b'
git diff origin/<기준 브랜치>...HEAD --stat
git diff origin/<기준 브랜치>...HEAD
```

커밋 메시지만 보고 쓰지 않는다. diff를 읽어야 "변경 이유"를 쓸 수 있다. 커밋 메시지는 "무엇을"을 말하고, 리뷰어가 알고 싶은 것은 "왜"다.

변경 파일 중 테스트 파일(`*.test.*`, `*.spec.*`, `__tests__/`)이 있으면 어떤 동작을 검증하는지 읽는다. `package.json`에 test 스크립트가 있으면 실행해 결과를 기록한다. 실행이 실패하거나 의존성이 없어 돌릴 수 없으면 그 사실을 테스트 절에 적는다. 돌리지 않은 테스트를 통과한 것처럼 쓰지 않는다.

### 3. 제목 작성

- 커밋이 하나면 그 커밋 제목을 그대로 쓴다.
- 커밋이 여럿이면 전체를 아우르는 제목을 `<타입>: <요약>` 형식으로 새로 쓴다. 타입은 commit 스킬과 같이 feat, fix, refactor, chore 중 하나다. 가장 큰 변경의 타입을 따른다.
- 한국어로 쓰고 50자 안팎, 마침표 없음. 코드 식별자와 라이브러리 이름은 원문을 유지한다.

### 4. 본문 작성

`${CLAUDE_SKILL_DIR}/references/pr-template.md`를 읽고 모든 섹션을 채운다. 꺾쇠 자리표시자(`<...>`)를 남기지 않는다. 쓸 내용이 없는 항목은 "없음" 또는 "해당 없음"으로 적는다.

섹션별 작성 기준:

- **변경 이유**: 이 변경이 없을 때 생기는 문제나 요구를 두세 문장으로 쓴다. 커밋 본문의 "왜"와 diff에서 읽은 맥락을 합친다.
- **변경 내용**: 커밋 단위로 불릿을 쓴다. 커밋 제목을 그대로 옮기지 말고, 리뷰어가 diff를 읽을 때 길잡이가 되도록 어떤 파일에서 무엇이 바뀌었는지 한 줄씩 덧붙인다.
- **테스트**: 실제로 실행한 항목은 체크(`[x]`)하고 결과를 적는다. 리뷰어나 사용자가 확인해야 할 항목은 체크하지 않은 채(`[ ]`) 둔다. UI 변경이면 수동 확인 항목을 적는다.
- **참고**: 브랜치 이름이나 커밋 메시지에 이슈 번호(`#123`, `issue-123`)가 있으면 적는다. 없으면 "없음". 스크린샷은 UI 변경일 때 "추가 필요"로 적고, 아니면 "해당 없음".

`$ARGUMENTS`에 추가 요청이 있으면 해당 섹션에 반영한다.

본문은 임시 파일에 쓴다. 쉘 인자로 넘기면 백틱, `$`, 따옴표가 깨진다.

```bash
BODY=$(mktemp)
cat > "$BODY" <<'EOF'
(채운 본문)

🤖 Generated with [Claude Code](https://claude.com/claude-code)
EOF
```

### 5. push와 PR 생성

```bash
git push -u origin <현재 브랜치>
gh pr create --draft --base <기준 브랜치> --head <현재 브랜치> --title "<제목>" --body-file "$BODY"
```

push가 거부되면(원격이 앞서 있음) 강제 push하지 않는다. 상황을 보고하고 끝낸다.

### 6. 보고

최종 보고에는 다음을 적는다. 사용자는 이 보고만 보고 PR 상태를 파악한다.

- PR URL과 제목, `기준 브랜치 <- 작업 브랜치`
- 담긴 커밋 수와 변경 파일 수
- 테스트 실행 여부와 결과
- 이 스킬이 정한 것: 기준 브랜치를 어떻게 골랐는지, 제목을 새로 썼는지
- Draft 상태이므로 본문을 확인한 뒤 Ready for review로 바꾸라는 안내

## 예시

입력: 브랜치 `feat/code-view`에 커밋 2개 (`chore: prism-react-renderer 의존성 추가`, `feat: 생성된 컴포넌트 코드 보기 패널 추가`), 기본 브랜치 main, `$ARGUMENTS` 없음.

출력(제목): `feat: 생성된 컴포넌트 코드 보기 패널 추가`

출력(본문 일부):

```
## 변경 이유

## 변경 내용
- prism-react-renderer 의존성 추가 (package.json, bun.lock)
- CodeView 컴포넌트 추가. 생성 결과를 tsx 구문 강조로 표시 (src/components/CodeView.tsx)
- App에서 Preview 아래에 CodeView 배치 (src/App.tsx)

## 테스트
- [x] bun test 실행, 12개 통과
- [ ] 브라우저에서 코드 패널 표시와 구문 강조 수동 확인

## 참고
- 관련 이슈: 없음
- 스크린샷: 추가 필요
```
